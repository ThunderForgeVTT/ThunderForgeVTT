# The Interaction Effect Contribution Seam

- **Date**: 2026-08-30
- **Status**: Accepted
- **Spec**: `specs/030-interactive-elements/`

## Context

Spec 030 gives a Game Master things on a scene that respond: a prop that opens
a lore entry, a lever that toggles lights, a door that opens, closes and locks,
a region that fires when crossed, and a request the GM must approve.

Read as a feature list that is six behaviours. Built as a feature list it
becomes one plugin that knows about lighting, walls, lore and navigation —
and, on the day audio exists, about audio too. Constitution Principle II
forbids exactly that: a plugin that cannot be removed without breaking the
others is not modular, and one that names every subsystem it can drive is
coupled to all of them.

The problem is sharper than ordinary coupling because **three surfaces must
agree on the vocabulary**. The engine dispatches an effect, the server
validates and persists it, and the web app offers it in an authoring form. Any
design where each holds its own list guarantees drift, and drift here is
silent in the worst way: a GM authors an effect nothing handles, and at the
table nothing happens. No error, no log. Spec 029 spent an entire user story
retiring that exact failure mode at the engine's command boundary.

There is also a subsystem that does not exist yet. Sound and music are unbuilt.
A design that enumerates effects has to decide what to do about the ones it
cannot perform — grey them out, hide them, flag them — and every one of those
answers is a maintenance surface for options that are dead by construction.

## Decision

### 1. Effects are contributed by the subsystem that performs them

`InteractionPlugin` owns placement, hit-testing, trigger detection, permission
resolution, `once` bookkeeping, and writing an activation event. It owns **no
effect at all**.

Every effect is contributed by its own subsystem: doors contribute
`door.set_state`, `door.set_lock` and `door.reveal`; lighting contributes
`light.toggle`; lore contributes `lore.open`; navigation contributes
`nav.request_scene`. The authorable vocabulary is the union of what is
compiled in.

This makes the unbuilt-subsystem question disappear rather than answering it.
Audio contributes nothing today because there is no audio, so nothing dead is
ever offered; the day it exists it contributes `audio.play` and nothing else
in the system changes.

### 2. Declarations live in `thunderforge-canvas-core`; handlers live in plugins

A declaration is **data** — id, label, description, subject kinds, typed
config fields. It carries no behaviour, because its three consumers need it in
three places.

`canvas-core` is the one crate the server already compiles and from which the
web app's TypeScript is already generated by `ts-rs`. One definition, three
consumers, and the generation check already wired into `pnpm verify` to catch
drift.

It is also the only crate where the rules can be *tested*. The engine crate
targets `wasm32-unknown-unknown` with no wasm-bindgen test runner: its
`#[cfg(test)]` modules compile and never execute. Any rule worth a test —
authoring validation, the activation truth table, region entry — therefore
has to live here, the same constraint that put spec 029's resource model here.

### 3. Dispatch crosses the plugin boundary as a Bevy event

`InteractionPlugin` writes one event per activation, after permission has
resolved. Each contributing plugin adds a system that reads those events and
filters for the identifiers it declared. No direct calls in either direction.

Constitution II names this: cross-plugin communication happens through Bevy
events or shared resources, never through direct calls into another plugin's
private systems. It is also the only shape under which the interaction plugin
compiles and runs with every contributor removed.

### 4. Absence is detected before dispatch, never after it

An event is fire-and-forget. "Nobody handled this" is not observable at the
call site, so an interactive whose subsystem is absent is detected by
comparing its stored `effect_id` against the assembled registry — not by
noticing that dispatch did nothing.

Such an interactive is reported *unavailable* to the GM, is not dispatched, is
not deleted, and reaches players as nothing rather than as an error. A GM who
loads a scene into a build without lighting has a switch they cannot use, not
a scene they have lost.

### 5. Collisions fail at assembly, not at first use

Two contributors declaring the same id fails when the registry is assembled —
at startup. Ids are namespaced by contributor, which makes the check a prefix
concern rather than a coordination problem.

A collision that surfaces only when a GM happens to author one of the two is a
collision found at the table, during a session, by the people least able to do
anything about it.

### 6. The engine dispatches optimistically; the server stays authoritative

Activation is a server mutation, and the server enforces lock, GM-only, fire
mode and approval. The engine may apply the visible change locally for
responsiveness, which Principle III explicitly permits, but it is never a
second authority on whether a door may open. Divergence between the two paths
is a client bug, never a disagreement to settle in the client's favour.

This matters most for the rule most likely to be got wrong: *a player cannot
open a locked door*. The tempting implementation is to not draw the button.
That passes every screen test and fails the moment somebody calls the mutation
directly, so the refusal is tested at the server.

## Consequences

**The claim is testable rather than asserted.** FR-039 is written textually as
well as behaviourally: the words "light", "door" and "sound" do not appear in
the interaction plugin's logic, and `scripts/verify.mjs` greps for them. A
violation is something anyone can see rather than a matter of judgement.

**Adding a triggerable capability never edits the core.** If it ever does,
that check should be failing, and the seam has stopped being a seam.

**Doors are the named risk.** They are the effect most tempting to build into
the interaction core, because they are the most obviously spatial. They are
contributed from `wall.rs` like anything else.

**An event cannot report that nobody listened**, which is why (4) exists.
Anything else that wants to know whether an effect ran will have to ask the
registry too, not the event.

**One honest incompleteness.** `nav.request_scene` raises a request and, on
approval, does nothing further, because multi-scene navigation does not exist.
The request and the decision are the parts this feature owns and they work;
the destination is future work. That is honest rather than dead.

## Alternatives Considered

- **A Rust enum of effect kinds.** Rejected outright. An enum lives in one
  crate, so every subsystem gaining a triggerable capability would edit the
  core — precisely the coupling Principle II forbids.
- **Engine owns the registry, server stores opaque blobs.** Rejected: the
  server could not then validate an authored effect, which Principle III
  requires at the data boundary, and the authoring UI would depend on a loaded
  wasm engine to know what a GM may choose.
- **A server manifest declares effects, as game systems declare resources.**
  Rejected: manifests describe *content* that varies per ruleset. Effects are
  capabilities of the build, and expressing them as data would let a manifest
  declare an effect no code can perform — the dead-option problem from the
  other direction.
- **A trait-object handler registry (`Box<dyn EffectHandler>`).** Rejected:
  handlers need `Commands` and arbitrary `Query` access, which a boxed trait
  cannot express without a service-locator shape that fights the ECS. Bevy's
  answer to "several systems care that a thing happened" is an event.
- **Open/Closed/Locked as a single enum.** Rejected: it makes "open, and
  players cannot close it" — a spiked-open portcullis — inexpressible, and
  forces a decision about what the lock becomes when a GM opens a locked door
  that a separate flag simply never raises.
