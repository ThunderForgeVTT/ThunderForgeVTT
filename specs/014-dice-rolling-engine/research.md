# Phase 0 Research: Dice Rolling Engine

## 1. Where the crate lives, and how each side depends on it

**Decision**: New workspace member `crates/thunderforge-dice` (package name `thunderforge_dice`), added to the root `Cargo.toml`'s `[workspace] members` list alongside the existing `crates/thunderforge-canvas-core` and `crates/pack_system_spec`. `src/server/Cargo.toml` and `src/engine/Cargo.toml` both add it as a plain path dependency (`thunderforge_dice = { path = "../../crates/thunderforge-dice" }`, matching exactly how `src/engine/Cargo.toml` already depends on `thunderforge_canvas_core`).

**Rationale**: The repo already has an established, explicitly-documented convention for exactly this shape of crate. `crates/thunderforge-canvas-core/Cargo.toml` carries the comment: *"Deliberately no `bevy`/`wasm-bindgen` dependency (Constitution Principle II: modular, independently testable)... engine code can pass Bevy `Vec2` values into this crate's functions with zero conversion."* That is precisely the pattern this feature needs — logic importable by both a native Axum server and a `wasm32-unknown-unknown`-compiled Bevy engine, with no engine/Bevy dependency baked into the shared crate itself. No new directory convention is invented; `crates/` is confirmed (by inspecting the actual root `Cargo.toml`) to already be the repo's home for this kind of thing, not `src/core` (which is `thunderforge_core`, a broader native-oriented library already pulled into `src/server` for auth/events/models/policies — not itself imported by `src/engine`, and not the right precedent to imitate here).

**Alternatives considered**:
- Adding the dice logic directly inside `src/server` and separately duplicating a simplified version inside `src/engine` (or a pack crate): rejected outright — this is exactly the "two competing implementations" failure mode the constitution's Principle I rationale describes for the old tldraw/Bevy split, and is concretely already happening today in `packs/systems/dnd5e/engine/src/dice.rs` (research.md §5) — a second, ruleset-specific, WASM-broken implementation this feature is meant to retire, not add a third variant of.
- Putting it in `src/core` (`thunderforge_core`): rejected — that crate is not consumed by `src/engine` today (confirmed by dependency inspection), and pulling in its existing deps (chrono, regex, base64, uuid-with-v7, etc.) into a WASM-compiled dice grammar crate would be unnecessary bloat for something that should stay as minimal as `thunderforge-canvas-core`.

## 2. Formula grammar: parser approach

**Decision**: Hand-rolled recursive-descent parser (tokenizer + Pratt-style precedence climbing for the arithmetic layer, explicit grammar functions for dice terms/modifiers/groups), implemented directly in `crates/thunderforge-dice/src/parser.rs` with zero parser-library dependency.

**Rationale**: The grammar in spec.md (FR-004 through FR-009a) is fully specified and bounded — base dice, a fixed, enumerable set of modifiers each with a small argument shape (optional count, or a comparison-condition), parenthetical/pool grouping, and four-function arithmetic plus a handful of named math functions. This is well within hand-rolled recursive-descent's comfort zone and keeps the crate's dependency list matching `thunderforge-canvas-core`'s established "as few dependencies as the job allows" philosophy (that crate's only dependency is `glam`, itself required for the actual math it does — not a convenience/tooling dependency). A parser-combinator crate (`nom`, `pest`, `chumsky`) would all compile fine to `wasm32-unknown-unknown` (they're pure-Rust, no OS calls) — that's not disqualifying — but they add a real dependency surface (and, for `pest`, a build-time grammar-file/codegen step) for a grammar small and stable enough that hand-writing it is not meaningfully more code, and keeps the crate approachable/auditable for a security-relevant boundary (FR-011's "reject malformed input, never guess" requirement is easiest to reason about when every parse branch is explicit, hand-written code rather than combinator-library internals).

**Alternatives considered**:
- `pest` (PEG grammar file + codegen): rejected — adds a build-time codegen dependency and a second grammar-description language (the `.pest` file) to keep in sync with spec.md's prose grammar; not justified for this grammar's size.
- `nom`: plausible, would work fine under wasm32; rejected mainly on "no dependency is more auditable than a well-chosen one, but here the grammar is simple enough that hand-rolling doesn't cost meaningfully more code," matching the minimal-dependency precedent set by `thunderforge-canvas-core`.
- `chumsky`: same reasoning as `nom`; also comparatively less battle-tested/lower-adoption than `nom`/`pest` for a crate that needs to be trustworthy at a security boundary.

## 3. RNG boundary: how the crate stays trustworthy without being target-aware

**Decision**: The crate's evaluator (`eval.rs`) takes an injected `&mut impl rand_core::RngCore` parameter on its public `resolve()` function — it never constructs, seeds, or reaches for any entropy source itself. `crates/thunderforge-dice`'s only RNG-adjacent dependency is `rand_core` (the trait-definition half of the `rand` ecosystem — no OS/thread/seeding facilities, and it compiles identically on every target including `wasm32-unknown-unknown`, since it has zero platform-specific code). `src/server` depends additionally on the full `rand` crate and constructs a real, OS-entropy-seeded RNG (e.g. `rand::rngs::StdRng::from_os_rng()` or `ThreadRng`) to pass into `resolve()` inside the `rollDice` mutation — this is the only place in the entire system a "real" (i.e., actually treated as authoritative) roll is produced. `src/engine` (WASM) may also call `resolve()` — for formula *validation* (FR-011, so a bad formula can be rejected client-side before even round-tripping to the server, as a UX nicety) and, if useful, for a non-authoritative optimistic local preview — but it is never wired to anything that treats its output as a final result; the GraphQL `rollDice` mutation (contracts/graphql-roll.md) is architecturally the only path that can ever produce a `world_roll_records` row or a value returned to other players, and it always re-resolves server-side regardless of what a client sends (FR-001/FR-002).

**Rationale**: This design means the crate needs zero `#[cfg(target_arch = "wasm32")]` branching internally (unlike the `packs/systems/dnd5e/engine/src/dice.rs` precedent it replaces, which hard-codes two divergent implementations behind a `cfg` and currently ships a non-functional, hardcoded-to-10 stub on the WASM side per its own `// Phase 4.8.1 will add crypto-based randomization for browser` comment). Trust is enforced at the *application/API* layer (only the mutation resolver ever persists/broadcasts a result), not inside the crate via capability-hiding — which is more robust, since it means even a client build that somehow got a "real" RNG wired up client-side still couldn't produce anything the rest of the system would accept as authoritative. This directly satisfies FR-001, FR-002, and FR-015.

**Alternatives considered**:
- `#[cfg(not(target_arch = "wasm32"))]`-gating real randomness inside the crate itself (mirroring the existing `dice.rs` pattern): rejected — this is the precedent this feature exists to fix. It couples the crate to target-detection instead of to an explicit, testable API contract, makes the crate harder to unit-test (seeded/deterministic tests become target-conditional instead of just "pass in a mock RNG"), and — as proven by the current `dice.rs`'s abandoned "Phase 4.8.1" TODO — is easy to leave half-finished on the WASM side.
- Having the crate depend on the full `rand` crate (with its `getrandom`/OS-entropy backends) directly: rejected — unnecessary weight for a crate that should work identically and be fully unit-testable via injected deterministic RNGs; `rand_core`-only keeps the crate's own test suite simple (mock `RngCore` implementations, no OS entropy needed to run `cargo test` on the crate itself) and keeps the WASM build lean (no `getrandom` wasm-feature wiring needed in the shared crate).

## 4. Bounding reroll/explosion/dice-count (FR-012)

**Decision**: `eval.rs` enforces two hard caps during evaluation, checked continuously (not just up front): a maximum total number of individual dice rolled across the whole resolution (covering the base dice plus every reroll/explosion-produced extra die), and a maximum number of reroll/explosion iterations *per die*. Both are fixed internal constants (generous enough to cover any real tabletop formula — spec.md's Assumptions explicitly call the exact numbers an implementation detail, not product behavior) exposed as public `const`s on the crate so `tasks.md`/tests can reference and exercise the boundary directly. Exceeding either cap during evaluation aborts resolution with a specific `FormulaError` variant (FR-011) rather than truncating silently.

**Rationale**: A condition like `x>=1` on a `d6` (explodes on any roll, including the exploded dice's own results) is a real, well-formed formula under this grammar that has no natural termination — the cap is what makes FR-012's "reject or cap... rather than hanging" guarantee actually true, and it must live inside the evaluator itself (not rely on every caller remembering to impose a timeout) since `resolve()` is meant to be a trusted, simple function to call correctly.

**Alternatives considered**:
- A wall-clock timeout wrapped around `resolve()` by each caller instead of an in-crate dice-count cap: rejected as the sole mechanism — timeout-based termination still burns CPU/allocates memory up to the timeout, and duplicating timeout-wiring in both `src/server` and `src/engine` callers is exactly the kind of caller-discipline-dependent safety net this crate should not require. A cap is deterministic, testable in isolation, and works identically for every caller with zero setup.

## 5. Superseding `packs/systems/dnd5e/engine/src/dice.rs`

**Finding**: `packs/systems/dnd5e/engine/src/dice.rs` (149 lines, pre-existing) already implements a narrow, D&D-5e-specific `roll_d20`/`RollAdvantage` API, `#[cfg(target_arch = "wasm32")]`-gated to a **non-functional stub that always returns a face value of 10**, with an explicit `// Phase 4.8.1 will add crypto-based randomization for browser` TODO comment — i.e. today, any dnd5e-pack code path that rolls a d20 in the browser build gets a fixed fake result, not a real roll. This is a direct, concrete instance of the exact problem this spec exists to solve, already live in the codebase.

**Decision**: This spec's own tasks build the new, general-purpose `thunderforge_dice` crate and its `rollDice` mutation; **migrating `packs/systems/dnd5e/engine/src/dice.rs`'s call sites onto the new crate is explicitly out of scope for this spec's task list** (that pack's integration is its own unit of work, and this spec should not silently absorb a second package's migration). It is instead recorded here, in plan.md's Constitution Check (Principle IV) and Complexity Tracking, as required follow-up: an ADR should record the decision to supersede `dice.rs`, and a small follow-up task/spec should migrate dnd5e's `roll_d20`/`RollAdvantage` call sites onto `thunderforge_dice::resolve()` with an equivalent `1d20` (+ advantage as `2d20kh1` / disadvantage as `2d20kl1`, both expressible directly in the new grammar per FR-005) formula, then delete `dice.rs`.

**Rationale**: Advantage/disadvantage in 5e is exactly "roll 2d20, keep the higher/lower one" — already representable without any special-casing under this spec's keep/drop modifiers (FR-005), so the migration is expected to be a deletion, not a redesign, once this spec ships. Calling this out now (rather than staying silent) matches Principle IV's intent and prevents a future contributor from treating the old `dice.rs` as still-current guidance.

## 6. Animation/presentation contract (Principle I boundary)

**Decision**: The dice-bouncing animation (User Story 4) is planned as a new Bevy plugin (`src/engine/src/plugins/dice_roll/`, per Constitution Principle II's per-capability-plugin rule), triggered by the `rollDice` GraphQL mutation's response arriving in the React/game-shell layer and forwarded into the engine (matching the existing pattern other world-state-driven engine effects use to receive server-pushed data). The plugin's only inputs are the per-die outcomes already present in the mutation's response (`GraphQLDieOutcome[]`, contracts/graphql-roll.md) — it does not call `resolve()` itself to "guess" an outcome to animate toward; it animates *to* the already-known resolved face values.

**Rationale**: Constitution Principle I requires canvas-adjacent presentation to live in Bevy plugins, not React/DOM — a dice-bouncing physics animation is squarely "drawn on the game canvas" territory. Keeping the animation purely a renderer of already-resolved data (never a second source of the outcome) is also what makes FR-015/FR-016 trivially true: the animation cannot disagree with the authoritative result because it never computes one.

**Alternatives considered**:
- A React/CSS or `<canvas>`-outside-Bevy dice animation: rejected per Principle I — this repo's constitution treats this as a hard boundary, not a preference, and dice-bouncing is exactly the kind of "drawn on the game canvas" interactive/physical element the principle reserves for the engine.
