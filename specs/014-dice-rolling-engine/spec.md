# Feature Specification: Dice Rolling Engine

**Feature Branch**: `014-dice-rolling-engine`

**Created**: 2026-08-23

**Status**: Draft

**Input**: User description: "can we build a dice rolling spec modeled on standard advanced tabletop dice-notation conventions (keep/drop, reroll, exploding, success-counting, etc.) i want it to be its own crate too so we can import it in the backend and frontend the goal is the frontend triggers the rolls displays the dice bouncing on screen but the backend is the determinator to avoid cheating and we should support all kinds of dice through formula allowing us to support any game system"

## Clarifications

*(No clarification session held — the request names a well-established family of tabletop dice-notation conventions (keep/drop, reroll/exploding, success-counting, etc., common across virtual tabletop tooling generally) and states its core architectural constraint explicitly (server-authoritative resolution, client presentation-only), leaving no critical ambiguity that couldn't be resolved with the reasonable defaults recorded in Assumptions below.)*

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A roll is requested and resolved fairly, with no client-supplied outcome ever trusted (Priority: P1)

Whenever anything in the app needs a dice outcome — a player attacking with a weapon, a DM rolling a saving throw, a healing potion's effect resolving — the request names a formula (e.g. `1d20+5`, `4d6kh3`, `2d8`) and is sent to be resolved. The actual random outcome is always determined in one authoritative place that every participant in the session implicitly trusts; no player's device is ever the source of the final number, so a modified or tampered client cannot produce a better result than a fair one would.

**Why this priority**: This is the entire reason the feature exists, per the request — without a trustworthy, tamper-proof resolution authority, a "dice engine" is worse than not having one, since it would create the appearance of fairness while being exploitable. Every other capability (formula breadth, animation) is worthless without this.

**Independent Test**: As any world member, trigger a roll for a simple formula (e.g. `1d20`); confirm the displayed result matches what the authoritative resolver actually determined (verifiable via a server-side log/record of the roll), and confirm that a request carrying a pre-computed or client-suggested result is ignored — the authority always (re-)determines the outcome itself.

**Acceptance Scenarios**:

1. **Given** a user triggers a roll for a formula, **When** the roll resolves, **Then** the outcome the user sees was generated by the authoritative resolver, never by the requesting client.
2. **Given** a malicious or modified client sends a roll request that includes a suggested/pre-rolled result alongside the formula, **When** the request is processed, **Then** the suggested result is ignored entirely and the authoritative resolver's own outcome is used instead.
3. **Given** two different users trigger the identical formula at the same time, **When** both rolls resolve, **Then** each is resolved independently and fairly (no result is derived from or influenced by the other).
4. **Given** a roll has resolved, **When** any world member later needs to verify what happened (e.g. a dispute over an outcome), **Then** a durable record of the resolved roll (formula, per-die results, final total, who/what triggered it, when) is available to at least the world's DM.

### User Story 2 - Any formula the table's game system needs can be rolled, not just basic dice (Priority: P1)

A game master or player enters or triggers a formula using standard tabletop dice notation — a plain die (`1d20`), a pool with arithmetic (`4d6+2`), keep/drop modifiers (`4d6kh3` — roll 4, keep the highest 3), reroll and exploding dice (`2d6r1`, `1d6x`), success-counting dice pools common to non-D&D systems (`8d10cs>=7`), clamped results (`1d20min1`), fate/genesis dice (`4dF`), and formulas that combine sub-rolls and math (`(2d4)d8`, `floor(1d20/2)`). The engine evaluates any well-formed formula in this notation correctly, so the app is not limited to D&D-style rolls and can support other tabletop systems' dice mechanics later without re-architecting the roll engine.

**Why this priority**: The request explicitly calls for supporting "all kinds of dice through formula allowing us to support any game system" — this is the feature's second core value alongside trust, and depends on User Story 1's resolution authority already existing (there must be something to hand the formula to).

**Independent Test**: Submit a representative formula from each supported category (plain die, arithmetic, keep/drop, reroll, exploding, success-counting, clamping, fate die, nested/math sub-expression) and confirm each resolves to a correct, well-formed result consistent with that notation's documented meaning; submit a malformed formula and confirm it is rejected with a clear error rather than silently producing a wrong or partial result.

**Acceptance Scenarios**:

1. **Given** a formula using plain dice and arithmetic (`4d6+2`), **When** it is resolved, **Then** the total equals the sum of the rolled dice plus the arithmetic, and every individual die's result is available (not just the total).
2. **Given** a formula using a keep/drop modifier (`4d6kh3`), **When** it is resolved, **Then** exactly the specified number of highest (or lowest) dice contribute to the total, and the dropped dice are still shown as rolled-but-excluded, not hidden.
3. **Given** a formula using a reroll or exploding modifier (`2d6r1`, `1d6x`), **When** it is resolved, **Then** the reroll/explosion behavior is applied exactly as the notation specifies, and the full chain of rolls (original plus every reroll/explosion) is available, not just the final kept value.
4. **Given** a formula using success/failure counting (`8d10cs>=7`), **When** it is resolved, **Then** the result reflects a count of dice meeting the condition, not a summed total, matching how dice-pool systems (e.g. World of Darkness-style games) interpret such a roll.
5. **Given** a formula using a fate/genesis die (`4dF`), **When** it is resolved, **Then** each die resolves to one of exactly three faces (+1, -1, or blank/0) and the total reflects their sum.
6. **Given** a formula with a nested sub-expression or math function (`(2d4)d8`, `floor(1d20/2)`), **When** it is resolved, **Then** the inner expression is evaluated first and its result correctly feeds the outer expression.
7. **Given** a malformed or unsupported formula (e.g. unbalanced parentheses, an unknown modifier, division by zero), **When** it is submitted, **Then** it is rejected with a clear, specific error before any dice are rolled — never silently mis-evaluated.

### User Story 3 - A formula can reference a character's stat instead of a hard-coded number (Priority: P2)

A formula author (e.g. an Item Effect from the Items & Inventory System) writes a formula that includes a named placeholder instead of a literal number — for example a weapon's attack roll written as `1d20 + STAT + MODIFIERS` rather than a specific number baked in at authoring time. When that formula is actually resolved for a specific character in play, the named placeholders are substituted with real values supplied by whatever is triggering the roll, and the engine evaluates the fully-substituted formula as normal.

**Why this priority**: This is what lets the engine "support any game system" in practice, not just in dice-notation breadth — a formula authored once (e.g. spec 013's Item Effects) must be resolvable against different characters' different stat values without rewriting the formula per-character or per-ruleset. It depends on User Story 2's formula evaluation already working, and is secondary to the raw roll-resolution/trust mechanics.

**Independent Test**: Resolve a formula containing a named placeholder (e.g. `1d20 + STR`) twice for two different supplied values of `STR` (e.g. 3 and -1); confirm each resolution correctly substitutes its own value and produces a correspondingly different total; attempt to resolve a formula whose placeholder has no supplied value and confirm a clear error rather than treating the missing value as zero or crashing.

**Acceptance Scenarios**:

1. **Given** a formula containing one or more named placeholders, **When** it is resolved with specific values supplied for every placeholder, **Then** each placeholder is replaced with its supplied value before the formula is evaluated.
2. **Given** the same formula is resolved twice with different supplied values for its placeholders, **When** each resolution completes, **Then** the two results differ in exactly the way the differing placeholder values would predict (e.g. a +2 difference in a stat produces a +2 difference in relevant sub-totals).
3. **Given** a formula references a placeholder for which no value was supplied at resolution time, **When** resolution is attempted, **Then** it is rejected with a clear error identifying the missing placeholder, rather than substituting zero or crashing.
4. **Given** a formula has no placeholders at all (a plain formula like `2d8`), **When** it is resolved, **Then** it behaves identically whether or not any placeholder values were supplied alongside it (no placeholder machinery is required to use the engine for simple rolls).

---

### User Story 4 - Players and the DM watch dice physically resolve, not just see a number appear (Priority: P2)

When a roll is triggered, everyone who should see it watches a short dice-bouncing animation that lands on the exact per-die results the authoritative resolver determined, before the final total is shown. The animation never determines or influences the outcome — it always plays out to reveal a result that was already decided — so there is no way to distinguish "waiting for the animation" from "waiting for the real roll," and no way for the animation's outcome to ever disagree with the authoritative result.

**Why this priority**: The request explicitly asks for the dice-bouncing display experience, but it is presentation layered on top of a resolved result — it depends on User Stories 1 and 2 (a real, trustworthy, fully-detailed result must already exist per die) and is not itself where the feature's core value or risk lives.

**Independent Test**: Trigger a roll and observe the animation; confirm every individual die shown bouncing lands on the exact face value present in the authoritative result (per User Story 2's "every individual die's result is available" requirement), and confirm the animation completing is what reveals the total — the total is never shown before or independent of the animation reaching its resolved state.

**Acceptance Scenarios**:

1. **Given** a roll is triggered, **When** the animation plays, **Then** each animated die comes to rest showing the exact face value that die actually resolved to in the authoritative result.
2. **Given** a roll involves a modifier that produces more dice than the base formula named (e.g. an exploding or rerolled die), **When** the animation plays, **Then** every die that was actually rolled (including rerolls/explosions) is represented in the animation, not just the dice named in the original formula.
3. **Given** the animation is playing, **When** a user inspects the displayed outcome before the animation finishes, **Then** no final total or misleading intermediate result is shown — the reveal is gated on the animation's completion.
4. **Given** a user's device is slow or the animation fails to play for any reason, **When** they wait, **Then** the correct final result still becomes visible (a broken/missing animation degrades to just showing the result, it never blocks or hides a resolved roll indefinitely).

### Edge Cases

- What happens when a formula requests an extreme number of dice (e.g. `10000d6`) or an unbounded exploding/reroll modifier that could loop indefinitely (e.g. an exploding condition that always matches, like `1d6x>=1`)? The engine enforces a sane bound on total dice rolled and/or reroll/explosion iterations per resolution, rejecting or capping formulas that would exceed it with a clear error, rather than hanging or exhausting resources.
- What happens when a formula divides by zero, or a math function receives an invalid input (e.g. rounding a formula that evaluates to a non-finite value)? Rejected with a clear error at resolution time, never silently coerced to zero/infinity or crashing the resolver.
- What happens when two users trigger rolls for the same formula at effectively the same instant? Each is an independent resolution — no shared or serialized "queue" behavior is required, and neither roll's outcome depends on the other's.
- What happens when a formula is syntactically valid but semantically nonsensical for how it's being used (e.g. a success-counting formula used where a plain total was expected)? Formula evaluation itself still succeeds and returns whatever the notation defines (a count, in that example) — matching the result's shape to a specific use case (e.g. "this is a damage roll, expect a total") is the responsibility of whatever triggered the roll, not the engine.
- What happens if the animation/presentation layer is entirely unavailable (e.g. accessed through a way that has no visual dice-bouncing surface)? The authoritative result is still delivered and usable — the animation is an enhancement, never a required step to obtain a valid result.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST resolve every dice roll's actual random outcome in exactly one authoritative place; no participant-supplied or client-originated value MUST ever be accepted as, or allowed to influence, a roll's outcome.
- **FR-002**: A roll request MUST be reducible to a formula string (plus, where applicable, named placeholder values per FR-010) and MUST NOT require or accept a pre-computed result from whatever triggered it.
- **FR-003**: The system MUST make the same formula-parsing and -evaluation capability available to both the authoritative resolution path and any presentation/animation path, so the two never interpret a given formula differently.
- **FR-004**: The system MUST support standard `NdM` die notation (e.g. `1d20`, `4d6`), arithmetic (`+ - * /`), and standard math functions (floor, ceiling, round, absolute value) within a formula.
- **FR-005**: The system MUST support keep/drop modifiers (keep-highest, keep-lowest, drop-highest, drop-lowest) with an optional count argument (defaulting to 1 when omitted).
- **FR-006**: The system MUST support reroll and exploding-dice modifiers (single reroll, recursive/repeated reroll, exploding, explode-once, explosion capped at a maximum count), each driven by a comparison condition (equals/greater-than/greater-or-equal/less-than/less-or-equal against a number).
- **FR-007**: The system MUST support result-clamping modifiers (raising results below a minimum, capping results above a maximum).
- **FR-008**: The system MUST support success/failure-counting dice-pool notation (count-successes, count-failures, deduct-failures, subtract-failures-by-face-value, even/odd counting, margin-of-success), so dice-pool-style tabletop systems are supported, not only summed-total systems.
- **FR-009**: The system MUST support parenthetical sub-expressions (including a die count or die size itself being a sub-roll, e.g. `(2d4)d8`) and dice-pool grouping with a shared modifier applied across grouped terms (e.g. keep-highest across several distinct dice groups).
- **FR-009a**: The system MUST support the Fate/Genesis die type (three faces: +1, -1, blank/0) as a distinct die notation alongside numeric `NdM` dice.
- **FR-010**: The system MUST support named placeholders within a formula that are substituted with caller-supplied values at resolution time (per User Story 3), and MUST reject resolution with a clear error identifying any placeholder left unsubstituted — it MUST NOT default a missing placeholder to zero or any other implicit value.
- **FR-011**: The system MUST reject a syntactically invalid formula (unbalanced grouping, unknown modifier, malformed condition, division by zero, non-finite math result) with a specific, actionable error, and MUST NOT roll any dice or return a partial/guessed result for an invalid formula.
- **FR-012**: The system MUST enforce a bound on total dice rolled (including rerolls/explosions) per single resolution, rejecting or capping a formula that would exceed it, so no formula can cause unbounded looping or resource exhaustion.
- **FR-013**: A resolved roll's result MUST expose every individual die's outcome (including every reroll/explosion that occurred), not only the final aggregated total, so a consuming display (per User Story 4) can represent exactly what happened.
- **FR-014**: The system MUST durably record each resolved roll (the formula used, every individual die outcome, the final result, who or what triggered it, and when), retrievable by at least the world's DM, to support after-the-fact verification of a disputed or reviewed outcome.
- **FR-015**: A presentation/animation layer consuming a resolved roll MUST only ever display outcomes that came from the authoritative resolution (per FR-001/FR-013) — it MUST NOT generate, guess, or pre-empt a result before the authoritative resolution completes.
- **FR-016**: The absence, failure, or unavailability of a presentation/animation layer MUST NOT prevent a resolved roll's result from being delivered and usable — animation is additive, never a precondition for a valid result.

### Key Entities *(include if feature involves data)*

- **Dice Formula**: A notation string expressing one roll request — base dice, arithmetic, modifiers, sub-expressions, and optional named placeholders — independent of any specific tabletop ruleset. The unit of input to resolution; the same shape already stored (inertly) as spec 013's Item Effect `formula` field.
- **Roll Resolution**: The authoritative act of evaluating one Dice Formula (with any placeholder values supplied) into a concrete result: every individual die outcome (including rerolls/explosions), any applied modifiers' effects, and the final aggregated value (a sum or a count, depending on the formula's notation). Always produced by the single authoritative resolution path (FR-001).
- **Placeholder Binding**: A named-value substitution supplied alongside a formula at resolution time (e.g. `STAT` → `3`), resolved into the formula before evaluation (User Story 3). The engine defines the substitution mechanism generically; what placeholder names exist and what values they carry for a given character/ruleset is supplied externally, not defined by this feature.
- **Roll Record**: A durable, retrievable log entry for one completed Roll Resolution — formula, full per-die detail, final result, triggering user/context, and timestamp (FR-014).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of delivered roll results originate from the authoritative resolution path — zero instances of a client-supplied or client-computed value being accepted as a final result, verifiable by comparing displayed results against Roll Records.
- **SC-002**: A representative formula from every supported notation category (plain dice, arithmetic, keep/drop, reroll, exploding, clamping, success-counting, fate die, nested sub-expression, placeholder substitution) resolves correctly on first attempt, with zero categories requiring a follow-up fix to produce a notation-correct result.
- **SC-003**: 100% of malformed or unbounded-risk formulas (invalid syntax, division by zero, runaway reroll/explosion, excessive dice count) are rejected with a clear error before any dice are rolled — zero instances of a hang, crash, or silently wrong result.
- **SC-004**: A triggered roll's animation and final result are visible to the triggering user within a few seconds under normal conditions, and the result remains fully available even when the animation cannot play.
- **SC-005**: An Item Effect formula authored under spec 013 (e.g. `1d20 + STAT + MODIFIERS`, `2d8`) can be resolved by this engine with zero changes required to spec 013's stored Item Effect data shape — this feature "unlocks" that already-scaffolded data rather than requiring it to be redesigned.
- **SC-006**: Every resolved roll is retrievable afterward (formula, per-die detail, final result, trigger, timestamp) by the world's DM, supporting 100% after-the-fact verifiability of disputed outcomes.

## Assumptions

- This spec defines the general-purpose dice-formula grammar, evaluation engine, and server-authoritative trust model only. It does NOT define any specific tabletop ruleset's mechanics (how a D&D 5e ability modifier is computed, what placeholders a given system exposes, how "advantage/disadvantage" maps onto notation, etc.) — that is a ruleset-specific layer built on top, consistent with spec 013's own "system-agnostic, ruleset layered on top" framing. This spec is what makes spec 013's Item Effect `formula`/`trigger_kind` fields resolvable, without requiring spec 013 to be redesigned (per the request and SC-005) — but wiring a specific Item Effect's `trigger_kind` (on-use vs. passive) into an actual gameplay trigger remains out of scope here too; this spec only makes "given a formula and placeholder values, produce a trustworthy result" possible.
- The dice-formula grammar supported (base dice, arithmetic, keep/drop, reroll/exploding, clamping, success/failure counting, fate dice, parenthetical/pool composition, math functions) targets the widely-used, common family of "advanced" tabletop dice-notation conventions found across virtual tabletop tooling generally (not any single product's exact syntax or proprietary behavior) — chat/flavor-text syntax, inline roll-embedding-in-prose conventions, and any specific tool's UI are explicitly out of scope; only the formula grammar and how it resolves is targeted.
- "One authoritative place" (FR-001) means a single logical resolution authority the rest of the system always defers to — this spec does not mandate a specific process/service topology (e.g. it doesn't require every world/session to share one physical resolver instance), only that no client-side code path is ever trusted to originate a final result.
- The named-placeholder substitution mechanism (User Story 3, FR-010) is a generic string-keyed value-binding step performed before formula evaluation — this spec does not define a schema, namespace, or resolution order for placeholder names (e.g. it doesn't decide whether `STAT` maps to Strength or something else for a given character); that mapping is supplied by whatever calls the engine (e.g. a future ruleset layer), matching spec 013's existing "target resource/attribute name expressed generically" precedent.
- A "reasonable bound" on total dice/rerolls/explosions per resolution (FR-012) is treated as a fixed, generous default sized to comfortably cover any real tabletop formula (e.g. thousands of dice, hundreds of reroll iterations) while still guaranteeing termination — the exact numeric limits are an implementation decision, not user-facing product behavior, and are not specified further here.
- Roll Records (FR-014) are retained indefinitely by default, consistent with how other durable per-world records in this app (e.g. lore revisions, per spec 012) are not given an automatic expiry unless stated otherwise; a future instance-level retention/quota policy remains out of scope, matching the precedent already set in spec 012's Assumptions for similar limits.
- The dice-bouncing animation (User Story 4) is a presentation concern with no bearing on fairness or correctness — this spec specifies only the contract between resolution and presentation (every die's real outcome must be available to drive it, and it must never gate or precede the authoritative result), not the animation's visual design, physics engine, or asset style, which are implementation/design decisions for the planning phase.
