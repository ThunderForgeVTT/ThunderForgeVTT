# Playtest — 2026-09-10

The owner, playing as GM against `make dev`, after spec 039 Phase 6 was
written (not yet committed). The second playtest round after the one this
spec came from (2026-09-01).

Each finding is in the owner's words first, then what was found and done.
"Cause" and "Fix" are filled in as they are established, not guessed.

## Defects

### P1. A placed character's token shows no image

> "When I place a character, the character token doesn't actually appear as
> an image on the screen."

- **Cause — two defects, which one depends on how it was placed:**
  1. **Place (the actors pane) creates no token at all.** Confirmed in code.
     The engine emits `token_placement_confirmed { kind: "actor", … }` on the
     click and removes its preview; the web's only listener
     (`InteractionTool.tsx:259`) returns early for anything but
     `kind === "prop"`, so nothing calls `createToken`. What it looks like: a
     pale square follows the cursor, the click makes it vanish, nothing
     remains, nothing is logged. Spec 031's T032 ("on confirmation, call the
     token-create mutation") is ticked but its actor half was never wired;
     commit eb8b1ad wired props only. Reopened in `tasks.md`.
  2. **A token that is created never shows the character's art.** The engine
     draws exactly one image, `tokens.photo_url`; neither `createToken` (token
     panel) nor bring-the-party copies the actor's `token` image from
     `world_actor_images` into it, and the token query has no fallback to it.
     Such a token is a plain coloured square.
  - **Latent, for the fix:** `/api/actor-assets/{id}` has no file extension,
    and Bevy picks a loader by extension, so pointing `photo_url` at it may load
    nothing — and a sprite whose image never loads draws nothing, with no
    fallback square. To be proven before relying on it.
- **Tests that would have caught it:** none. `canvas-authoring.spec.ts`
  begins a placement and cancels it; nothing places and confirms, and nothing
  checks an engine sprite's image loaded (`render_probe` can, and no e2e uses
  it for tokens).
- **Fix:**
  - Place: `pages/world/usePlaceActorTokens.ts` answers an actor's drop with
    `createToken` at the drop point; the world event brings the token to
    every client. Spec 031 T032 is closed with it.
  - Art: a token with no photo of its own resolves to its character's
    `token` image when read (`graphql/token_art.rs`), in the scene's token
    list and in every token mutation's answer — so it covers Place, the token
    panel, bring-the-party and existing tokens, and follows the art when it
    is replaced. The URL ends in `.webp`, which the character-image route now
    accepts (and 404s Bevy's `.meta` probe, as the canvas route does).
  - Who may load it: the character's *token* image only, for anyone who can
    see a scene carrying that token (`scene_visibility`'s rule); otherwise a
    player saw nothing at all where an NPC's token stood. Tested for a
    visible scene, a hidden one, a stranger and a character with no token.
  - Engine: a token whose art fails to load draws its colour swatch instead
    of nothing (`fall_back_when_token_art_fails`).
  - e2e: `canvas-authoring.spec.ts` › "Place creates a token, and the token
    shows the character's own art".
  - **Open:** a token placed for an NPC is typed `character` (the drop
    carries only the actor id). Its art is right; its kind colour and label
    are not until someone sets them.

### P2. Left click still leaves a yellow dot

> "I'm still getting the left click yellow dot problem."

"Still": seen before this round. The 2026-09-01 playtest recorded it as a
little yellow square appearing after switching to "the light tool or any other
tool" (finding #16, this spec's FR-040/FR-040a, research R6, T015/T016). Four
commits on 2026-09-01 gated each tool's input to its own mode. R6's browser
check of *where* the square lands was never recorded as done.

- **Cause — very likely, from code; not yet reproduced in a browser:** closing
  the tool rail leaves the engine armed with the last tool, deliberately
  (`WorldPage.tsx:390-399`: "Closing the rail entirely leaves the engine armed
  with whatever it had"). If that tool was Lights, every left click on the map
  places a light (`systems/lighting.rs:197-237`), drawn as an 18px square in
  pale amber, yellow when selected (`lighting.rs:47-54`). The rail shows no
  tool, so nothing says one is armed. The 2026-09-01 fix made each tool's input
  run only in its own mode — correct, and beside the point, because the mode
  itself outlives the rail.
- **Proposed fix:** closing the rail returns the engine to Select, which is an
  existing mode (not an invented "no tool" one) and in which a click on empty
  map only deselects. An e2e: pick Lights, close the rail, click the map; no
  light is created and `authoring_mode()` reads select.
- **Fix:** closing the rail returns the engine to Select (`WorldPage.tsx`,
  the `setAuthoringMode` effect: `effectiveGmToolId ?? "select"`). e2e:
  `canvas-authoring.spec.ts` › "closing the rail disarms the tool, so a click
  on the map places nothing" — with a control step proving that a click with
  Lights armed *does* place a light, so "nothing placed" cannot mean "the
  click never arrived".

### P3. Right-drag and middle-drag do not pan the map

> "I can't right click or middle mouse button to drag the map around."

- **Cause — confirmed in code:** panning with the mouse was never built.
  Arrow-key panning was removed on 2026-08-26 (`plugins/camera.rs:65-68`,
  "Panning is the mouse's job"); no mouse pan replaced it. There is no
  `MouseMotion`, middle-button or drag-to-pan code in the engine or the web;
  `CameraManager::pan()` is called only from tests, which is why the camera
  tests pass. The only right-button handling opens the context menu on press
  (`context_menu.rs:131`). ADR-032's plan named "middle-mouse drag or
  space+drag" and it stayed a stub.
- **Proposed fix:** middle-drag and right-drag pan in the engine's camera
  plugin. Right-click still opens the context menu, but on release without
  movement rather than on press, so a drag is not a menu. Mind the trap:
  `advance()` eases the camera towards `target_translation` every frame, so a
  pan must move the target, not just the translation. An engine test that a
  drag moves the camera through input (not by calling `pan()`), and an e2e
  that a middle-drag moves the view and a still right-click still opens the
  menu.
- **Fix:** middle-drag and right-drag pan (`plugins/camera.rs`,
  `handle_drag_pan`), grab-the-map: the point grabbed stays under the
  pointer. The math is in `thunderforge_canvas_core::camera` (`drag_pan`,
  `is_drag`, a 4px click/drag threshold), with unit tests that the grabbed
  point stays put at any zoom. `CameraManager::drag_by` moves the camera and
  its easing target together, so the map follows the hand instead of gliding
  behind it. The context menu now fires on release, and only when the
  pointer did not travel past the threshold. Engine tests drive a real
  middle-drag and a still right-click through Bevy's input messages — not
  `pan()` — and a dev-only `window.__engineProbe.camera()` lets e2e see the
  camera: `canvas-authoring.spec.ts` › "a middle-drag and a right-drag both
  pan; a still right-click does not".
- **Found on the way:** there is no right-click menu on the play field at
  all. The engine emits `canvas_context_menu`; nothing in the web listens for
  it (the only web code touching context menus suppresses the browser's own).
  The release-and-threshold logic is ready for when one exists.

## Design notes

### P4. About and Feedback belong inside the play field, not over it

> "We added an About and Feedback but they really should be more integrated.
> They're on screen, and they're hard to see. They should be integrated into
> the playfield, in the settings side or maybe their own unique identifiable
> button."

- **Found:** both sit in corners other play-field controls paint over, from
  class and z-index values; not yet confirmed on screen.
  - About (`AboutInstance`, mounted at `WorldPage.tsx:2629`) is
    `fixed bottom-3 left-3 z-[900] opacity-70`, dim on purpose. The GM tool rail
    (`z-[1040]`, 3rem wide) covers its left edge, and the dice roller shares the
    corner.
  - Feedback (`FeedbackLauncher`, mounted app-wide in `main.tsx`) is
    `fixed right-4 bottom-4 z-50`. The dock rail (`z-[1050]`) covers its right
    edge, any open dock section covers it entirely, and the Tokens toggle
    overlaps it.
  - About came from spec 039 FR-056 (the notice contact is discoverable without
    an account); Feedback from spec 037 FR-001 (reachable from any screen).
    Both requirements hold if the controls move into the dock, whose rail is
    always on screen and is shown to every role.
- **Proposed:** an "About & feedback" dock section, last after Settings, for
  every role, holding the About links and a "Send feedback" button; the
  floating About removed from the play field and the floating Feedback
  launcher hidden there. `e2e/play-field-about.spec.ts` moves with it, and
  feedback gains its first play-field e2e.
- **Decision (owner, 2026-09-10):** their own dock button — the "About &
  feedback" section as proposed.
- **Fix:** an "About & feedback" dock section, last after Settings, for every
  role (`PlayDock/HelpPanel.tsx`): a "Send feedback" button that opens the
  same `FeedbackDialog` the rest of the app uses (a sign-in note for a
  signed-out visitor, since the resolver refuses anonymous feedback), and the
  footer's legal links, still opening in new tabs (`AboutLinks`, extracted
  from `AboutInstance`). The floating About control is no longer mounted on
  the play field, and the app-wide `FeedbackLauncher` stands down on
  `/world/:id/play`. e2e: `play-field-about.spec.ts` now opens the dock tab,
  asserts nothing floats over the map, reaches the links, and opens the
  feedback form without navigating away.

### P5. A GM sets clocks, time, combat and selection directly

> "I'm playing as the GM right now. There should not be a start Genie
> session. There should just be clocks and time, to be able to just set those;
> same with combat and selection."

- **Found:** "Genie" is the co-op house game system (spec 018), not an
  assistant, and its session is the Wish Pool / Doom Clock / Puzzle Clock loop.
  - Combat and selection are **not** gated by it: combat has its own start
    buttons (`CombatPanel`), selection is the GM rail's Select tool.
  - "Time" does not exist: "Clocks & Timers" is only the dock label, and the
    only clocks are Genie's. System-neutral clocks are spec 029's open F001.
  - The button should not normally appear: new worlds get a session on
    creation (`start_session_for_new_world`). It appears because the seeded
    Demo World is inserted by raw SQL with no session row
    (`seeds/demo_accounts.sql`), and it comes back after any session is won or
    lost.
  - The gate is the server's (Principle III): every clock mutation is keyed by
    an active session.
- **Proposed, inside the Genie pack:** a GM with no active session gets one
  started automatically rather than a button; a concluded session offers
  "Reset clocks" instead; the demo seed gets its session row. Setting a clock
  to a value (rather than advancing it) is a new mutation and a note on spec
  018. System-neutral clocks and time are F001 and need their own spec.
- **Decision (owner, 2026-09-10):** auto-start and "Reset clocks", as
  proposed, inside the Genie pack; the demo seed gets its session row. Setting
  clock values directly and system-neutral clocks and time are not in this
  change.
- **Fix:**
  - The query: `genieSession` returns the latest session, whatever its status
    (`session/queries.rs`). Answering `null` for a won or lost session is what
    made "just concluded" look like "never started". Pack test:
    `a_concluded_session_is_still_returned`.
  - The panel (`SessionPanel.tsx`): no "Start Genie session" button. A world
    with no session at all gets one started, once, when its Game Master opens
    the panel ("Starting the session…" meanwhile); a won or lost session stays
    on screen with its outcome, and the Game Master gets "Reset clocks", which
    starts the next with the same Doom Clock size. Players see the outcome.
  - The seed: `demo_accounts.sql` gives the Demo World its session row, as
    every world created on the system gets one — the raw INSERT never ran the
    pack's creation hook.
  - The hook's comments no longer claim the query returns only active
    sessions.
  - e2e: the seven Genie session specs, which already clicked Start only when
    it was shown.

### P6. A selected token's health sits above it, not pinned to the screen

> "While a token is selected, the health bars should be above the token and
> not pinned on screen unless the user specifically double clicks the token,
> and they can drag that pin around."

Reported after P1–P5 were fixed, in the same session.

- **Found:**
  - The engine already draws bars above every token that has status
    (`plugins/status_display.rs`) — children of the token, so they follow it
    and zoom with the camera, culled off-screen, and fed only the values the
    server lets this viewer see. But they are sized and placed from the fixed
    `TOKEN_SIZE` (96px), not the token's grid footprint, so on most scenes they
    sit inside a large token or float off a small one. Not yet confirmed on
    screen.
  - Separately, selecting a token opens a React `StatusPanel` pinned to one of
    four screen corners, chosen from a "Panel position" select and kept in
    `localStorage`. It cannot be dragged or pinned; one at a time.
  - Double-click is already caught, in the DOM (`WorldPage.tsx`'s capture
    `dblclick` on the canvas), and only opens the stacked-token picker when
    two or more tokens are selected; on one token it does nothing. The engine
    deliberately does not detect double-clicks (two fast clicks often land in
    one Bevy frame).
  - The ask contradicts spec 029 as written — FR-010 (selection presents a
    screen-corner panel), FR-011 and US5 (a viewer-chosen corner) — and
    refines FR-006 (bars attached to the token) and FR-012 (no panel without a
    selection). FR-013–FR-016, disclosure, are unaffected.
- **Decision (owner, 2026-09-10, as stated in the note):** the bars above the
  token are the selected token's display; the screen panel appears only when
  the token is double-clicked, and is pinned and draggable. Implementation
  choices made to deliver it, and recorded as spec 029's amendment: the bars
  are sized from the token's footprint; one pinned panel at a time, opened at
  the double-click point, kept until closed or replaced by double-clicking
  another token (so a pin outlives the selection); its dragged position kept
  per viewer on this device, replacing the stored corner.
- **Fix:**
  - Bars: sized and placed from the token's footprint on the grid
    (`plugins/status_display.rs`, the same calculation as
    `size_tokens_to_grid`), and repainted when the grid or a token's footprint
    changes. Engine test: on a 50-unit grid a one-cell token's bars are 50
    wide and start just above it, a two-cell token's 100.
  - Panel: `StatusPanel` is a pinned panel — placed by position, dragged by
    its header (or nudged with the arrow keys), kept on screen, closed with
    "Unpin status panel". Selection no longer opens it; `WorldPage`'s
    existing `dblclick` handler pins the selected token, where the viewer
    last left a panel or at the double-click the first time, and the dragged
    position is kept in `localStorage` (`thunderforge.statusPanel.pin`). The
    four-corner picker and its stored corner are gone.
  - Spec 029 amended: FR-010 and FR-011 superseded by FR-010a and FR-011a,
    FR-012 refined by FR-012a, `PanelPlacement` and US5 annotated.
  - Tests: `placement.test.ts` (position, close, keyboard nudge, staying on
    screen, disclosure wording unchanged) and `status-placement.spec.ts` —
    selection opens nothing; a double-click pins at the click; a drag moves
    it; it outlives the selection; it closes; after a reload the next pin
    opens where the last was left.

### P7. Token names above tokens

> "Let's see if we can get token names appearing above tokens and sticking
> with them when they move, configurable by GM to hide it, players always
> visible."

Read as: a name above every token, following it as it moves; the Game Master
can hide a token's name from players; the Game Master always sees it.

- **Found:** the engine already draws text (`Text2d`, Bevy's built-in ASCII
  mono font); a token's `label` reaches the engine only on spawn, never on
  update; in practice every real token's label is empty, since no creation
  path sets one; and a player can already read any NPC's name two other ways
  — the `worldActors` list and the combat tracker — so hiding it on the token
  alone would not protect it.
- **Decision (owner, 2026-09-10):** every token shows its name to everyone by
  default; the Game Master can hide any token's name from players, and always
  sees every name (hidden ones drawn dimmed). A hidden name is withheld from
  the token and from the combat tracker in this change; the character list
  (where players read NPC names) gets its own change, since taking NPCs out of
  it changes what players can open.

### P9. Walls do not shade properly

> "Also e2e our engine and validate walls, because they aren't shading
> properly in the play test."

- **Cause — confirmed in code, several layers deep:**
  1. **The shading layer never turns on.** `plugins/darkness.rs` draws the
     darkness sheet and the wall-shadow mesh only when the scene's ambient
     light is dim or dark, and despawns both otherwise; `Bright` is the
     default, and nothing in the product ever sets ambient (only the engine
     sandbox sends `set_ambient_light`). `e2e/engine-lighting-limits.spec.ts`
     *asserts* zero shadow quads, pinning the broken state as expected. What
     is left visible is tokens dimming or vanishing, on a map at full
     daylight.
  2. **Imported walls, doors and lights are in the map image's pixel space**
     (origin top-left, y down: `map_import/geometry.rs` scales grid units and
     does nothing else), while the map art, the grid, tokens and hand-drawn
     walls are centred with y up. Imported geometry lands offset by half the
     map and mirrored vertically. The `walls` table records nothing that says
     which rows were imported, so correcting stored rows needs care.
  3. **Shadows are built only for lights near the camera at build time** and
     are not rebuilt on pan.
  4. **One light's shadows darken other lights' pools**, because shadows are
     one global overlay rather than per light.
  5. Token-carried lights are shaded at their stored position, not the
     token's; the grid, walls, light markers and pasted images draw above the
     darkness; no real player's token is given line of sight; and the
     `shadow_quads` statistic counts meshes, not quads.
  - Tests: the occlusion *maths* is unit-tested well; nothing tests that
    `DarknessPlugin` draws anything, and no e2e looks at shading.
- **Decisions (owner, 2026-09-10):**
  - Scenes default to bright; the Game Master sets bright, dim or dark per
    scene; an imported map takes the ambient level its file records.
  - New imports land in the engine's space; scenes imported before the fix
    are corrected by importing the map again. Stored rows are not migrated —
    imported and hand-drawn walls cannot be told apart, and a migration would
    move a GM's own walls on those scenes.

### P10. Shape drawing does not work

> "Also the shape drawing isn't working."

- **Cause — confirmed in code:** the Shapes panel's sub-tool buttons
  (Freehand, Rectangle, Ellipse, Line) were never connected to the engine.
  `ShapeTool.tsx` says so itself: selecting one "only signals intent via
  local UI state today". The engine decides what a drag draws from
  `ActiveShapeTool`, which starts `None` and is written only by the number
  keys 1–5 while the canvas has keyboard focus; there is no web-to-engine
  command for it (`sdk.rs` knows only `upsert_shape` and `remove_shape`). With
  no kind set, a drag in Shapes mode selects or moves an existing shape and
  creates nothing, silently.
  - Why the suite passed: every drawing e2e presses 1–4 instead of clicking
    the buttons, which routes around the missing wiring.
  - Not today's rail-close change — but since it, the key workaround also
    stops once the rail is closed.
  - Found beside it: the Text tool places text in container-relative screen
    pixels, sent as world coordinates, so it lands away from the click and
    mirrored vertically; and the colour picker writes `style.color` while the
    engine reads `style.colorIndex`, so colour changes do nothing.
- **Fix:**
  - The buttons arm the engine: a new `set_active_shape_tool` export
    (`plugins/shape.rs`) queues the kind, and a system applies it on the next
    frame — the same request-slot shape as the engine's other web commands.
    Clicking the pressed button again disarms it, and leaving Shapes mode
    clears the kind, so a tool never outlives its panel. Engine test:
    `the_toolbar_arms_the_shape_a_drag_draws`.
  - Text lands under the click: `engine/bevy/screenToWorld.ts` makes the
    engine's own conversion (canvas centre is the camera, one pixel is
    `scale` world units, y flipped), fed by the engine's `camera_state()`.
    Unit-tested at any zoom and canvas offset.
  - Colour is a palette of swatches in the engine's `COLOR_PALETTE` order,
    writing `style.colorIndex` — the field the engine reads.
  - e2e: `canvas-authoring.spec.ts` › "The Shapes panel's own buttons" —
    clicks Rectangle and Ellipse and drags, places text and checks it lands at
    the world point under the click, and recolours with a swatch. No number
    key is pressed anywhere in it.
