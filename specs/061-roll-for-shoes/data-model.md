# Data Model: Roll for Shoes

**Feature**: `specs/061-roll-for-shoes` | **Date**: 2026-09-22

Roll for Shoes stores four things about a character and nothing else. Two of
them are plain values, one is the actor's own name, and one — the skill
lineage — is the only structure in the game.

There are **no new tables and no new columns**. Everything below lives in the
JSONB slots of `world_actor_system_data` that every system pack already has,
and the pack's own validators are what give those slots a shape.

---

## Character

Not a record of its own. A Roll for Shoes character *is* a
`world_actors` row whose `game_system_id` is `roll_for_shoes`, plus its
system-data slots.

| The spec's word | Where it lives | Notes |
|---|---|---|
| name | `world_actors.label` | the product's own field; the pack adds nothing |
| description | `trait_data.description` | free text, may be absent or empty |
| XP | `resource_data.xp` | integer, ≥ 0, absent reads as 0 |
| skills | `trait_data.skills` | see **Skill** below |

Three of the four slots a pack may use are unused: no `ability_data` (the game
has no attributes), no `proficiency_data`, no `spell_data`. Absence is the
correct answer, not a gap.

### `resource_data`

```json
{ "xp": 0 }
```

`xp` is also declared as a manifest `resources` counter, so it is drawn
wherever the product draws a system's counters — including on a token — without
the pack asking.

### `trait_data`

```json
{
  "description": "Kicked out of the cobbler's guild. Still has the shoes.",
  "skills": [
    { "id": "s-root", "name": "Do Anything", "level": 1, "parentId": null },
    { "id": "s-2", "name": "Run Away From Trouble", "level": 2, "parentId": "s-root" }
  ]
}
```

## Skill

| Field | Type | Rule |
|---|---|---|
| `id` | string | non-empty, unique within the list, opaque, generated by the sheet |
| `name` | string | non-empty; **free text**, not unique, never an identifier |
| `level` | integer | ≥ 1; equals the number of d6 the skill rolls; no upper bound |
| `parentId` | string or null | null for the root; otherwise the `id` of another skill in the same list |

**Rules**

1. A character's list, once written, holds **exactly one root** — a skill with
   `parentId: null` — and that root is at `level: 1`. It is `Do Anything`
   at creation and is never removed or replaced (FR-039).
2. A non-root skill's `level` **equals its parent's level plus one** (FR-033).
3. `id` is not shown to anybody and carries no meaning. It exists so a skill
   can be pointed at after its name has been reused, because names are free
   text and two skills may share one.
4. Cycles are impossible rather than forbidden: rule 2 makes the level strictly
   increase along every parent link, and a cycle would require a level greater
   than itself. The validator therefore checks the level relation and gets
   acyclicity without a traversal.
5. There is no cap on `level` (FR-040). A roll of more than 1000 dice is
   refused by the dice engine, which is a fact about one resolution, not about
   the character — see research D7.

**What a skill is not**: it is not an ability, not a proficiency, and not a
manifest `check`. It cannot be declared, because it does not exist until a
player says it out loud.

## Roll attempt

**Not stored by this pack.** It lives for the length of one interaction on the
sheet, and the server keeps its own durable copy in `world_roll_records` the
way it does for every roll.

| Field | Where it comes from |
|---|---|
| skill | chosen by the player from their own list |
| dice | the server's resolution — one `d6` per level, each with its face |
| total | the resolution's sum |
| opposition | a number the player records from the Game Master, or absent |
| verdict | `success` when total > opposition, `failure` when total ≤ opposition, `unjudged` when no opposition was given |
| bought sixes | how many dice the player has converted with XP, this attempt |

**State**

```
        roll
  idle ──────► rolled ──┬── verdict: failure ──► +1 XP
                        ├── verdict: success ──► no change
                        └── verdict: unjudged ─► no change
                                │
                       every die (rolled or bought) shows 6
                                ▼
                         advancement offered
                           │           │
                     name given    declined
                           ▼           ▼
                    skill granted   nothing
```

The XP award and the advancement offer are **independent**: a roll that both
fails and shows all sixes does both (FR-041). Buying a six never revisits the
verdict, the total or the XP already awarded (FR-028).

## Validation

Enforced in the pack's own `server/` crate, through the two validators it
contributes. A rejection is a GraphQL error carrying the message below, and
the sheet renders it rather than swallowing it (research D8).

### `resource_data`

| # | Rule | Message |
|---|---|---|
| R1 | must be a JSON object | `resource_data: must be a JSON object` |
| R2 | `xp`, if present, is an integer | `xp: must be an integer` |
| R3 | `xp` is at least 0 | `xp: must not be negative` |

### `trait_data`

| # | Rule | Message |
|---|---|---|
| T1 | must be a JSON object | `trait_data: must be a JSON object` |
| T2 | `description`, if present, is a string | `description: must be text` |
| T3 | `skills`, if present, is an array | `skills: must be a list` |
| T4 | each entry is an object with `id`, `name`, `level` | `skills[i]: must be an object with id, name and level` |
| T5 | `id` is a non-empty string, unique in the list | `skills[i].id: must be unique and not empty` |
| T6 | `name` is a non-empty string | `skills[i].name: must not be empty` |
| T7 | `level` is an integer of at least 1 | `skills[i].level: must be a whole number of at least 1` |
| T8 | `parentId` is null or the `id` of another entry | `skills[i].parentId: must name another skill` |
| T9 | with a parent, `level` is the parent's level plus one | `skills[i].level: must be one higher than its parent` |
| T10 | a non-empty list has exactly one entry with `parentId: null` | `skills: must have exactly one starting skill` |
| T11 | that root is at level 1 | `skills: the starting skill must be at level 1` |

The validator deliberately checks **nothing about a name's specificity or its
relevance** (FR-036). That judgement belongs to the table, and a system that
arbitrated it would be playing the game for them.

---

## What this feature adds to existing entities

Nothing. No migration, no schema change, no new GraphQL type, no new root
field. The pack is discovered from its directory, its data is stored in slots
that already exist, and its rolls go down the path every other roll takes.
